在智能饮食健康管理助手项目中，嵌入式端承担着最贴近用户的感知与交互任务，是整个系统的“眼睛”和“前台”。
具体来说，嵌入式端围绕一块 ESP32-P4 芯片展开，它需要完成从物理世界采集数据、在本地运行轻量级 AI 模型、与用户交互，
再到将结果上报云端等一系列工作，核心目标是在不依赖网络的情况下实时分析食物，同时兼顾低功耗与响应速度。

首先，嵌入式端通过摄像头持续采集餐盘的图像。摄像头通常采用 MIPI-CSI 接口与 ESP32-P4 连接，拍摄角度固定，
能够清晰捕获食材摆放区域。每一帧图像会被送入已经在端侧部署好的 YOLO11n 模型——这是一个经过量化的、
大小仅几兆字节的超轻量目标检测网络。模型会在本地完成推理，输出类别标签和置信度。
由于推理过程完全在芯片内部的神经网络加速器或 CPU 上运行，不依赖云端，所以响应速度可以控制在数秒内。
YOLO11n 的输出结果主要包括：发现了哪几种食材、每种食材的位置和大致的尺寸（通过边界框面积估算），
并能够统计每种食材的数量。例如，它可以在一个餐盘里同时框出两块鸡胸肉、几朵西兰花和数片胡萝卜。

除了视觉信息，嵌入式端还连接了一个或多个压力传感器，通常安装在餐盘下方或餐具底部。当用户开始用餐时，
压力传感器会连续测量餐盘整体的重量变化。通过记录进食前后的重量差值，系统可以较为精确地获取每种食材被吃掉的实际重量。
由于 YOLO 模型只能给出食材种类和数量，无法知道具体克数，压力传感器就起到了“秤”的作用。每次重力传感器数值发生变化就会拍一次照，
这样在食物一个一个放上去的过程中就可以通过对比秤的数值和yolo识别结果来得知每个食物分别重多少克

下一步是营养计算，这也是第二个端侧 AI 的工作。用户在使用时，
会通过屏幕上的按键或语音（如果集成了简单的语音识别模块）输入他们即将采用的烹饪方式，例如爆炒、清蒸、红烧、油炸等。
然后，嵌入式端将 YOLO 识别出的食材种类、压力传感器得到的食材重量以及用户选择的烹饪方式一起输入到第二个轻量级模型中。
这个模型是预先训练好的 LightGBM 树模型（通过代码生成的方式内嵌在 ESP32-P4 中），
它的任务是输出这顿饭烹饪后的预估总热量、蛋白质、脂肪、碳水化合物等营养信息（11项）
但有时候有些数据会因为原始数据表的缺少或其他原因导致数值为0，数值为零的一律在前端不显示。
这一步的关键在于模型在训练时已经学习了不同烹饪方式对营养变化的影响（例如油炸会显著增加热量和脂肪，
水煮会损失部分钾和维生素 C）。模型推理的时间很短，通常在几十毫秒内完成，
因此用户可以很快在屏幕上看到“这一餐吃完后大概会摄入多少热量”这样的反馈。

为了让用户直观地看到结果，嵌入式端还需要驱动一块显示屏（通常是 MIPI-DSI 接口的彩色 LCD）。
屏幕上会显示：摄像头实时画面（可选）、识别出的食材清单、估算的重量、选择的烹饪方式，
以及最终计算出的总热量、蛋白质等数据。
用户也可以通过触摸屏（如果是触摸屏）来修正烹饪方式或手动调整重量。

最后，嵌入式端负责与云端或后端服务器通信。它通过外接的 Wi-Fi 模块（例如 ESP32-C6）将每餐的识别结果
（食材、重量、烹饪方式、营养值）以及用户的身份信息打包，通过 HTTP 协议发送到 Go 后端。
同时，它也可以接收后端下发的长期健康规划摘要（例如“本周建议控制每日总热量在 1800 千卡以内”），并在屏幕上显示，
提醒用户。如果网络不稳定，嵌入式端可以暂时将数据存储在本地 Flash 或 PSRAM 中，待网络恢复后再补传。

总的来说，嵌入式端在项目中既是数据采集者（摄像头、压力传感器），又是本地 AI 推理的执行者（YOLO 检测 + 营养估算），
还是人机交互的终端（屏幕显示、按键/语音输入）。
它把重计算的云端任务（如长期规划、体检报告分析）与实时性、隐私性要求高的前端任务（食材识别、即时营养计算）清晰地分离开，


智能饮食健康管理助手 — 项目技术说明
============================================

一、系统架构概述
----------------

本项目是一个端侧智能饮食管理系统，核心计算全部在嵌入式设备本地完成，不依赖云端推理。
系统以 ESP32-P4 芯片为中心，集成摄像头、压力传感器、显示屏和 Wi-Fi 通信模块，
实现从食物识别到营养估算的全链路本地化处理。

云端后端（Go 语言）仅负责长期数据存储、健康趋势分析和规划建议下发，
不参与任何实时推理或营养计算。即使网络断开，嵌入式端仍可独立完成全部核心功能。


二、硬件组成
------------

| 组件              | 型号/接口          | 作用                                       |
|-------------------|--------------------|-------------------------------------------|
| 主控芯片          | ESP32-P4           | 运行两个 AI 模型、驱动外设、管理通信       |
| 摄像头            | MIPI-CSI 接口      | 采集餐盘图像，供 YOLO 检测食材             |
| 压力传感器（多个）| 安装于餐盘下方     | 实时测量餐盘重量变化，精确获取食材克数     |
| 显示屏            | MIPI-DSI 接口 LCD  | 显示识别结果、营养数据、用户交互界面       |

三、端侧处理全流程（核心）
--------------------------

整个流程分为五个阶段，全部在 ESP32-P4 上完成：

【阶段1】图像采集与食材识别

  - 摄像头持续采集餐盘图像
  - 图像送入端侧部署的 YOLO11n 模型（量化后仅几 MB）
  - YOLO 在本地完成推理，输出：
    · 食材类别（对应 final.json 中的 31 种食材）
    · 每种食材的位置（边界框）
    · 每种食材的数量（通过边界框计数）
  - 推理完全在芯片内运行，不依赖网络，响应时间数秒内

【阶段2】重量获取（压力传感器 + 摄像联动）

  - 压力传感器连续测量餐盘总重量
  - 每次传感器数值发生变化（即用户放入新食材），自动触发一次拍照
  - 通过对比前后两次重量差值与 YOLO 识别结果，精确推算每种食材的克数
  - 举例：餐盘原重 200g，放入一块鸡肉后变为 380g，YOLO 识别出鸡肉，
    则鸡肉重量 = 380 - 200 = 180g
  - 此机制解决了 YOLO 只能识别种类和数量、无法给出克数的问题

【阶段3】用户输入烹饪方式

  - 用户通过屏幕按键或语音选择烹饪方式
  - 可选的 7 种烹饪方式：

    | 编码 | 英文键名   | 中文     |
    |------|-----------|----------|
    | 0    | boil      | 煮       |
    | 1    | braise    | 红烧/炖  |
    | 2    | deep_fry  | 炸       |
    | 3    | pan_fry   | 煎       |
    | 4    | roast     | 烤       |
    | 5    | steam     | 蒸       |
    | 6    | stir_fry  | 炒       |

【阶段4】本地营养预测（LightGBM 模型）

  - 将食材种类、重量、烹饪方式组合为 41 维特征向量（见第五节）
  - 送入 11 个独立的 LightGBM 树模型（已通过代码生成内嵌于 ESP32-P4）
  - 模型输出 11 项烹饪后营养数据（见第六节）
  - 推理耗时几十毫秒，用户几乎无感知
  - 执行后处理（见第七节），确保物理合理性

【阶段5】结果展示与数据上报

  - 显示屏实时展示：
    · 识别出的食材清单及重量
    · 用户选择的烹饪方式
    · 11 项营养预测值（数值为 0 的项目不显示）
  - 同时将结果通过 Wi-Fi 上报云端（见第九节）
  - 网络中断时暂存本地 Flash/PSRAM，恢复后补传

七、后处理规则（模型推理后必须执行）
--------------------------------------

11 个模型独立预测，可能出现物理不合理的结果。推理后必须执行以下修正：

【规则1】所有输出裁剪非负

  所有 11 个输出值，小于 0 的一律取 0。
  原因：回归模型在训练稀疏区域可能输出微小负值（如脂肪 -0.2g），
  这不代表"有负数的营养"，而是模型判断"接近零"时数学上轻微越界，
  裁剪到零是最接近真值的合理估计。

  C 代码：
    for (int i = 0; i < 11; i++) {
        if (results[i] < 0.0f) results[i] = 0.0f;
    }

【规则2】能量用 Atwater 公式重算（覆盖模型输出）

  energy_kcal = 4 * protein_g + 9 * fat_g + 4 * carbohydrate_g

  此步骤彻底消除三大营养素与热量之间的物理不一致，保证能量守恒。
  不要直接使用模型输出的能量值。

  C 代码：
    results[1] = 4.0f * results[2] + 9.0f * results[3] + 4.0f * results[4];

十、端云职责划分
-----------------

| 职责                     | 执行方    | 说明                                      |
|--------------------------|----------|-------------------------------------------|
| 食材图像识别（YOLO）     | 嵌入式端 | 本地推理，实时响应                        |
| 食材重量获取             | 嵌入式端 | 压力传感器 + 摄像联动                     |
| 烹饪方式输入             | 嵌入式端 | 用户通过按键/语音/触摸选择                |
| 营养预测（LightGBM）     | 嵌入式端 | 11 个模型本地推理，几十毫秒完成           |
| 后处理（裁剪+Atwater）   | 嵌入式端 | 保证物理合理性                            |
| 结果展示                 | 嵌入式端 | LCD 屏显示，数值为 0 不显示               |
| 每餐数据上报             | 嵌入式端 | HTTP 上传，断网暂存                       |
| 长期数据存储             | 云端     | 历史餐食记录、营养趋势                    |
| 健康规划与分析           | 云端     | 体检报告分析、长期饮食建议                |
| 规划建议下发             | 云端     | 推送摘要到嵌入式端显示                    |

核心原则：实时性要求高的任务（识别、称重、营养计算）全部在端侧完成，
云端只做非实时的长期分析与规划，系统在断网时仍可正常使用。
