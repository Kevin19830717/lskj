# 端侧智能饮食健康管理助手 - 人工智能/机器学习课程汇报大纲

## 项目概述

### 1. 项目背景与意义
- **问题背景**：现代人饮食不均衡，缺乏便捷的饮食营养管理工具
- **传统方案局限**：需要人工记录、依赖云端计算、响应延迟
- **创新点**：端侧AI模型，实时本地推理，不依赖网络
- **技术挑战**：嵌入式设备计算资源有限，需要轻量级高效模型

### 2. 项目目标
- **技术目标**：在ESP32-P4嵌入式设备上实现完整的饮食营养分析
- **功能目标**：食材识别 → 重量测量 → 营养预测 → 数据显示
- **性能目标**：实时响应（秒级）、高精度（R² > 0.9）、低功耗

## 系统架构设计

### 3. 硬件系统架构
```
ESP32-P4 核心处理单元
├── MIPI-CSI 摄像头（图像采集）
├── 压力传感器阵列（重量测量）
├── MIPI-DSI LCD触摸屏（用户交互 + 显示）
├── ESP32-C6 Wi-Fi模块（数据上报）
```

### 4. 软件处理流程
1. **图像采集与食材识别**：YOLO11n模型本地推理
2. **重量获取**：压力传感器 + 摄像联动
3. **烹饪方式选择**：LCD触摸屏输入（7种方式）
4. **营养预测**：LightGBM模型本地推理
5. **结果显示**：LCD显示 + 云端上报

## 机器学习模型部分

### 5. 模型选择：LightGBM的优势
- **轻量级**：适合嵌入式设备部署，决策树文本格式可直接转为C代码
- **高效率**：推理速度快，内存占用小，11个模型串行推理约9ms（PC端）
- **高精度**：梯度提升决策树，平均R²达0.9385
- **可解释性**：特征重要性清晰，便于调试和优化
- **部署友好**：通过m2cgen可转为纯C代码，无运行时依赖

### 6. 数据准备与特征工程
- **数据来源**：20,000条合成数据（Kevin数据集）
- **数据生成策略**：连锁反应模型v2
  - 只随机化少数"烹饪条件参数"（水分、添加油/盐/糖、热强度、水溶流失）
  - 所有营养变化由这些条件物理推导，保证能量守恒和营养一致性
- **特征维度**：41维特征向量
- **特征构成**：
  - 索引0~30：31种食材one-hot编码（对应食材填1.0，其余0.0）
  - 索引31~34：第1~4种食材重量(g)
  - 索引35：所有食材重量之和(raw_weight_total)
  - 索引36：平均重量(raw_weight_mean)
  - 索引37：食材数量(1~4)
  - 索引38：是否含水果(has_fruit, 0/1)
  - 索引39：是否含肉类(has_meat, 0/1)
  - 索引40：烹饪方式编码(0~6)

### 7. 模型训练与验证
- **训练策略**：11个独立回归模型（多目标回归），每个模型预测一种营养素
- **训练框架**：LightGBM + Python (sklearn)
- **评估指标**：R²、RMSE、MAPE
- **性能指标**：
  - 平均R²：0.9385
  - 平均MAPE：19.8%

### 8. 模型部署与优化
- **模型转换**：LightGBM .txt → C代码（m2cgen库），内嵌于ESP32-P4 Flash
- **内存评估**：
  - 11个模型文件总计：13,430 KB（13.1 MB），共2,472棵决策树，155,736个叶节点
  - 运行时输入：41维float = 164 bytes (RAM)
  - 运行时输出：11个float = 44 bytes (RAM)
  - 推理栈空间：几KB (RAM)
  - ESP32-P4: 768KB SRAM + 外部PSRAM，内存充足
- **后处理规则**（保证物理合理性）：
  - 规则1：所有输出裁剪非负（回归模型在训练稀疏区域可能输出微小负值）
  - 规则2：能量用Atwater公式重算，覆盖模型输出
    - `energy_kcal = 4 * protein_g + 9 * fat_g + 4 * carbohydrate_g`
    - 保证三大营养素与热量之间的物理一致性（能量守恒）

## 端侧AI实现细节

### 9. 食材数据库设计
- **数据结构**：31种食材，每种含23项营养数据（每100g可食部）
- **食材分类**：水果类11种、肉类5种、蔬菜类9种、香辛料3种、蛋类1种、豆制品1种、其他1种
- **数据格式**：final.json内嵌于设备，用于UI显示参考
- **重要**：模型推理时不直接读取final.json，输入是41维特征向量

### 10. 特征构建逻辑
- **One-hot编码**：31种食材选择，对应位填1.0
- **重量处理**：支持1~4种食材组合，未用位填0.0
- **统计特征**：总重量、平均重量、食材数量
- **类别标志**：自动判断是否含水果/肉类
- **烹饪方式**：7种编码（煮0/红烧/炖1/炸2/煎3/烤4/蒸5/炒6）

### 11. 模型推理流程
```
1. 输入：41维特征向量（食材one-hot + 重量 + 烹饪方式）
2. 串行推理：11个LightGBM模型各自独立预测
3. 后处理：非负裁剪 + Atwater公式重算热量
4. 输出：11项营养数据
5. 显示：数值为0的项目不显示
```
