智能饮食健康管理助手 — 项目技术说明
============================================

一、系统架构概述
----------------

本项目是一个端侧智能饮食管理系统，核心计算全部在嵌入式设备本地完成，不依赖云端推理。
系统以 ESP32-P4 芯片为中心，集成摄像头、压力传感器、显示屏和 Wi-Fi 通信模块，
实现从食物识别到营养估算的全链路本地化处理。

云端后端（Go 语言）仅负责长期数据存储、健康趋势分析和规划建议下发，
不参与任何实时推理或营养计算。即使网络断开，嵌入式端仍可独立完成全部核心功能。


二、硬件组成
------------

| 组件              | 型号/接口          | 作用                                       |
|-------------------|--------------------|-------------------------------------------|
| 主控芯片          | ESP32-P4           | 运行两个 AI 模型、驱动外设、管理通信       |
| 摄像头            | MIPI-CSI 接口      | 采集餐盘图像，供 YOLO 检测食材             |
| 压力传感器（多个）| 安装于餐盘下方     | 实时测量餐盘重量变化，精确获取食材克数     |
| 显示屏            | MIPI-DSI 接口 LCD  | 显示识别结果、营养数据、用户交互界面       |
| Wi-Fi 模块        | ESP32-C6（外接）   | 与云端后端 HTTP 通信，上报数据/接收建议    |
| 触控/按键         | 触摸屏或物理按键   | 用户选择烹饪方式、修正识别结果             |


三、端侧处理全流程（核心）
--------------------------

整个流程分为五个阶段，全部在 ESP32-P4 上完成：

【阶段1】图像采集与食材识别

  - 摄像头持续采集餐盘图像
  - 图像送入端侧部署的 YOLO11n 模型（量化后仅几 MB）
  - YOLO 在本地完成推理，输出：
    · 食材类别（对应 final.json 中的 31 种食材）
    · 每种食材的位置（边界框）
    · 每种食材的数量（通过边界框计数）
  - 推理完全在芯片内运行，不依赖网络，响应时间数秒内

【阶段2】重量获取（压力传感器 + 摄像联动）

  - 压力传感器连续测量餐盘总重量
  - 每次传感器数值发生变化（即用户放入新食材），自动触发一次拍照
  - 通过对比前后两次重量差值与 YOLO 识别结果，精确推算每种食材的克数
  - 举例：餐盘原重 200g，放入一块鸡肉后变为 380g，YOLO 识别出鸡肉，
    则鸡肉重量 = 380 - 200 = 180g
  - 此机制解决了 YOLO 只能识别种类和数量、无法给出克数的问题

【阶段3】用户输入烹饪方式

  - 用户通过屏幕按键或语音选择烹饪方式
  - 可选的 7 种烹饪方式：

    | 编码 | 英文键名   | 中文     |
    |------|-----------|----------|
    | 0    | boil      | 煮       |
    | 1    | braise    | 红烧/炖  |
    | 2    | deep_fry  | 炸       |
    | 3    | pan_fry   | 煎       |
    | 4    | roast     | 烤       |
    | 5    | steam     | 蒸       |
    | 6    | stir_fry  | 炒       |

【阶段4】本地营养预测（LightGBM 模型）

  - 将食材种类、重量、烹饪方式组合为 41 维特征向量（见第五节）
  - 送入 11 个独立的 LightGBM 树模型（已通过代码生成内嵌于 ESP32-P4）
  - 模型输出 11 项烹饪后营养数据（见第六节）
  - 推理耗时几十毫秒，用户几乎无感知
  - 执行后处理（见第七节），确保物理合理性

【阶段5】结果展示与数据上报

  - 显示屏实时展示：
    · 识别出的食材清单及重量
    · 用户选择的烹饪方式
    · 11 项营养预测值（数值为 0 的项目不显示）
  - 同时将结果通过 Wi-Fi 上报云端（见第九节）
  - 网络中断时暂存本地 Flash/PSRAM，恢复后补传

五、模型输入：41 维特征向量构建规则
------------------------------------

嵌入式端必须按以下顺序构建 41 维 float 数组，作为 11 个模型的共同输入：

| 索引  | 字段名              | 类型  | 填充规则                              |
|-------|--------------------|-------|---------------------------------------|
| 0~30  | ing_食材英文名      | float | 对应食材 one-hot 填 1.0，其余 0.0     |
| 31    | raw_weight_1        | float | 第 1 种食材重量(g)                    |
| 32    | raw_weight_2        | float | 第 2 种食材重量(g)，无则 0.0          |
| 33    | raw_weight_3        | float | 第 3 种食材重量(g)，无则 0.0          |
| 34    | raw_weight_4        | float | 第 4 种食材重量(g)，无则 0.0          |
| 35    | raw_weight_total    | float | 所有食材重量之和                      |
| 36    | raw_weight_mean     | float | raw_weight_total / 食材数量           |
| 37    | n_ingredients       | float | 食材数量 (1~4)                        |
| 38    | has_fruit           | float | 食材中含水果则 1.0，否则 0.0          |
| 39    | has_meat            | float | 食材中含肉类则 1.0，否则 0.0          |
| 40    | cooking_method_enc  | float | 烹饪方式编码 (0~6，见第三节阶段3)     |

食材数量上限：4 种（raw_weight_1~4 只有 4 个位置）

重量输入注意事项：
  - 普通食材：50~500g
  - 香辛料特殊范围：pepper 0.5~5g，garlic/ginger 5~30g
  - 重量单位均为克(g)，指食材的毛重（未经可食部比例折算）

七、后处理规则（模型推理后必须执行）
--------------------------------------

11 个模型独立预测，可能出现物理不合理的结果。推理后必须执行以下修正：

【规则1】所有输出裁剪非负

  所有 11 个输出值，小于 0 的一律取 0。
  原因：回归模型在训练稀疏区域可能输出微小负值（如脂肪 -0.2g），
  这不代表"有负数的营养"，而是模型判断"接近零"时数学上轻微越界，
  裁剪到零是最接近真值的合理估计。

  C 代码：
    for (int i = 0; i < 11; i++) {
        if (results[i] < 0.0f) results[i] = 0.0f;
    }

【规则2】能量用 Atwater 公式重算（覆盖模型输出）

  energy_kcal = 4 * protein_g + 9 * fat_g + 4 * carbohydrate_g

  此步骤彻底消除三大营养素与热量之间的物理不一致，保证能量守恒。
  不要直接使用模型输出的能量值。

  C 代码：
    results[1] = 4.0f * results[2] + 9.0f * results[3] + 4.0f * results[4];

九、与云端后端的通信
---------------------

嵌入式端通过外接 ESP32-C6 Wi-Fi 模块，以 HTTP 协议与 Go 后端通信。

【上行】嵌入式 → 云端

  每餐结束后，嵌入式端上报 JSON 数据，格式：

  {
    "user_id": "设备唯一标识",
    "timestamp": "2026-06-04T19:00:00+08:00",
    "ingredients": ["chicken", "carrot", "potato"],
    "raw_weights_g": [200.0, 80.5, 150.0],
    "cooking_method": "braise",
    "nutrition": {
      "cooked_weight_g": 389.6,
      "cooked_energy_kcal": 452.3,
      "cooked_protein_g": 40.2,
      "cooked_fat_g": 12.5,
      "cooked_carbohydrate_g": 33.1,
      "cooked_sodium_mg": 1240.0,
      "cooked_cholesterol_mg": 106.0,
      "cooked_vitamin_c_mg": 8.4,
      "cooked_calcium_mg": 56.0,
      "cooked_iron_mg": 3.8,
      "cooked_potassium_mg": 712.0
    }
  }

  字段说明：
  - ingredients: 字符串数组，1~4 个食材，必须是 final.json 中 31 种食材的英文键名
  - raw_weights_g: 浮点数数组，与 ingredients 一一对应，单位克(g)
  - cooking_method: 字符串，7 种烹饪方式之一的英文键名
  - nutrition: 11 项营养预测值（已执行后处理）

【下行】云端 → 嵌入式

  后端下发长期健康规划摘要，例如：
  - "本周建议控制每日总热量在 1800 千卡以内"
  - "近7天平均蛋白质摄入偏低，建议增加肉蛋类"
  - 网络不稳定时，数据暂存本地 Flash/PSRAM，恢复后自动补传


十、端云职责划分
-----------------

| 职责                     | 执行方    | 说明                                      |
|--------------------------|----------|-------------------------------------------|
| 食材图像识别（YOLO）     | 嵌入式端 | 本地推理，实时响应                        |
| 食材重量获取             | 嵌入式端 | 压力传感器 + 摄像联动                     |
| 烹饪方式输入             | 嵌入式端 | 用户通过按键/语音/触摸选择                |
| 营养预测（LightGBM）     | 嵌入式端 | 11 个模型本地推理，几十毫秒完成           |
| 后处理（裁剪+Atwater）   | 嵌入式端 | 保证物理合理性                            |
| 结果展示                 | 嵌入式端 | LCD 屏显示，数值为 0 不显示               |
| 每餐数据上报             | 嵌入式端 | HTTP 上传，断网暂存                       |
| 长期数据存储             | 云端     | 历史餐食记录、营养趋势                    |
| 健康规划与分析           | 云端     | 体检报告分析、长期饮食建议                |
| 规划建议下发             | 云端     | 推送摘要到嵌入式端显示                    |

核心原则：实时性要求高的任务（识别、称重、营养计算）全部在端侧完成，
云端只做非实时的长期分析与规划，系统在断网时仍可正常使用。
